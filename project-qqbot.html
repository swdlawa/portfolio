A bot that picks itself back up

At first I just wanted a character in the group chat that could hold a conversation. Somewhere along the way I learned that making a model talk is easy; keeping it online for weeks is hard.

Role
Solo developer
Time
2026.05
Stack
NoneBot2 · NapCat · DeepSeek API
Outcome
Months of uptime in a live group

What I wanted

Four requirements, on paper: a fixed persona, memory of the conversation, the ability to understand images, and scheduled reminders. Technically that's one chain: a QQ message arrives, the model answers, the reply goes back.

The hard part is that the chain can't run once. Messages arrive at any hour; machines reboot, networks drop, APIs time out. A bot that only works during a demo is pointless.

Choosing the stack

  • NoneBot2 for message dispatch and plugins — a Python ecosystem, quick to modify.
  • NapCat to talk to QQ over the OneBot 11 protocol.
  • DeepSeek API for replies, with the persona fixed in a system prompt.
  • A WebSocket connection instead of HTTP, to receive events.

The bug that cost me a night

I configured the HTTP adapter exactly as documented. The startup log said everything was fine, but the bot never reacted to a message. All "success", zero connections on the port.

It took hours to confirm: the adapter was reporting that its config had loaded, not that it was actually listening. Switching to a WebSocket connection made events arrive immediately.

"Reports success, listens on nothing" — the worst class of bug, because every log is lying to you.

After that I added two layers of insurance: a daemon that restarts the process if it dies, and start-on-boot so a reboot doesn't matter. Health is judged by a real probe request, not the last line of a log.

How memory works

No vector database. Each conversation keeps the last few turns, truncated when it gets long. It's enough, and it's cheap. The persona is pinned through the system prompt so it doesn't slowly become someone else.

Image understanding converts the image into a model input and asks about it. Accuracy is mediocre, so I never let it make important judgements about an image.

Where it stops

  • Long contexts get expensive, so only the last few turns are kept — no long-term memory.
  • The model occasionally makes things up; for factual questions it's instructed to say it isn't sure.
  • There's no complex per-group permission model. It runs in a small group of friends.

What I learned

I used to think deployment was the last step. Now I know it's the first. What makes a service usable is the unglamorous part: timeouts, retries, supervision, logs. This project is also where I started appending a question to every "success" log line: did it actually succeed?
