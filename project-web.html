让 AI 写代码，然后为它负责

这是学校的课程项目，也是我第一次完整地做“前端 + 接口 + 数据库 + 部署”。AI 帮了大忙，但每一行提交的代码我都得能解释。

角色
课程项目 · 独立开发
时间
2026.09 — 11
技术栈
Vue 3 · FastAPI · MySQL · Docker
结果
可部署的完整站点

项目是什么

一个带登录、数据管理和后台的 Web 应用。前端 Vue3，后端 FastAPI，数据存 MySQL。功能本身不复杂，但“完整”这两个字意味着每一层都要自己接上：表单要校验、接口要鉴权、数据库要建表、部署要能重启。

AI 在哪些环节帮了忙

  • 脚手架：项目结构、路由、基础组件，省掉了大量查文档的时间；
  • 样板代码：增删改查接口、表单校验、JWT 的签发与校验；
  • 报错解释：把堆栈贴进去，通常能快速定位到方向。

但它也会自信地给出跑不通的代码：字段名对不上、依赖版本冲突、鉴权中间件顺序错了。这些只能靠实际跑一遍发现。

我怎么 review

我的做法比较笨，但有效：

  1. 先跑，跑不通就不看；
  2. 跑通之后逐段读，问自己“这行删掉会怎样”；
  3. 把关键路径写成测试，改坏了能立刻知道；
  4. 提交前看一遍 diff，确认没有夹带无关改动。

最典型的一次：AI 生成的登录接口看起来没问题，但 token 过期时间写成了硬编码，测试环境永远不过期。这种错误不会报错，只会在上线后变成安全问题。

AI 可以写代码，但不能替你承担“这段代码为什么在这里”的责任。

部署踩的坑

本地一切正常，用 Docker Compose 起服务后接口 500。第一反应是代码问题，最后发现是容器里的数据库还没准备好，后端就急着连。加了健康检查和重试之后才稳定。

看容器日志是这个阶段最重要的技能：docker compose logs -f 比猜测快一百倍。

如果重做一次

  • 先写接口契约，再让 AI 生成前后端，减少字段对不上的返工；
  • 测试跟着功能一起写，而不是最后补；
  • 把配置全部抽成环境变量，不在代码里留硬编码。
